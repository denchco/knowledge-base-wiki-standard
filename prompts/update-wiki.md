# Update an existing Wiki safely

Use this prompt when the user asks an implementation agent to update an existing Wiki to a released Standard stack.

## Starting instruction

```text
Update this existing Wiki to the approved immutable DenchCo Standard release.
Read prompts/update-wiki.md from the Standard repository and complete its workflow.
Preserve the Wiki's subject, evidence, local settings and documented deviations.
Open the implementation PR for manual approval unless I have authorised another outcome.
```

Resolve the target repository and update authority from the user's request and existing session. Do not repeat an approval already given. Ask one sequential `Question 1 of N` only when a material unknown prevents safe work. A read-only update check grants no implementation, merge or deployment authority.

## Instruction to the implementation agent

1. Read the target's nearest agent instructions, manifest, mapped authoring policy, selected profile, dependency contract, status and validation queue. Query its graph when available. Continue through its graph report and the smallest relevant canonical files when recall is incomplete. Record its current release tag and full Standard revision, Git and Jujutsu state, verification commands and last known working consumer commit.
2. Establish a separate clean review boundary. Preserve the user's uncommitted work. Stop and report conflicting local modifications, unresolved merges, missing history or ambiguous ownership. Do not reset, stash, overwrite, kill services or change evidence status to make the update proceed.
3. Select the exact target release. For an unnamed target, run `npm run standard:stack -- check <wiki> --json` and `npm run standard:stack -- resolve --json` from a trusted Standard checkout. Capture the published, non-draft, native-immutable release, full tag-to-commit resolution and successful trusted `Verify` push/main evidence at that commit. Bind the migration to that tag and full SHA. If the user already approved an exact target, verify that target's same evidence directly. Do not silently substitute a newer release. Stop on missing, changed, failed or ambiguous evidence. A local tag or explicit `--standard-revision` dry-run alone does not prove release qualification.
4. Read the target Standard source at that full commit. Compare it with the consumer's pinned source. Use `conformance:diff` and `conformance:upgrade-plan` for requirement and manifest review. These commands are read-only and the upgrade plan covers the manifest. Produce a separate implementation review for the complete applicable component changes.
5. Inventory release changes and map each to its actual consumer-owned path. Include dependency declarations, frozen locks, runtime versions, adapters, templates, configuration, generated-asset builders, checks, fixtures and CI where selected. Review unchanged supporting files that the changed components depend on. Record applicability, a reason for each exclusion, planned additions and removals, expected local hashes, proposed hashes and an ordered verification plan. Check current security advisories through the frozen-stack audits. Historical release verification is dated evidence.
6. Preserve the subject corpus, source identities and access boundaries, evidence states, unknown OKF/frontmatter fields, role mappings, local URLs, branding, reader settings, profile, deployment adapter and documented deviations. Merge relevant Standard contract changes into local contracts. Do not replace consumer content with the Standard's help, evidence, source register, starter records or deployment. Require a reviewed adaptation where local implementation differs from the reference.
7. Save the reviewed component plan and its digest outside canonical source until the target's own record policy requires otherwise. Immediately before implementation, recheck the consumer commit, file hashes, modes and clean boundary. Any mismatch stops that patch. Preserve the changed bytes and report the conflict. Re-plan the affected component before continuing. A recipe or checksum report supplies review evidence and has no apply authority.
8. Implement the authorised migration as a reviewable patch. Recheck preconditions before each ordered component and after any new user or tool change. Carry each component's full applicable dependency and proof closure together. Install with the selected exact runtime and frozen commands such as `npm ci` and `uv sync --frozen`. Install the browsers matched to the locked Playwright version where required. Do not resolve packages independently to their newest versions.
9. Rebuild only declared derived outputs. Run current audits, conformance validation and the target's complete selected-profile verification against the target implementation. Include graph generation, strict build, native runtime integrity, source/evidence controls and both-engine desktop/mobile browser checks where applicable. A bounded migration fixture cannot replace these checks. Distinguish passing, failed, waived, inapplicable and unrun obligations.
10. Run the component preservation check before changing adoption metadata. Where target validation needs a proposed pin or snapshot, review it explicitly in the isolated candidate branch and mark adoption pending. After all target checks pass, record adoption of the target's release tag and exact Standard revision together. Retain unknown metadata and local deviations. Record the migration evidence and any new source identities under the target's policy. Run complete final-tree verification again so the receipt binds the recorded pin. A failed final gate leaves adoption incomplete.
11. Inspect the final diff and preservation results. Record the required Jujutsu development-turn commit when the target uses Standard Production maintenance. Follow existing user authority for a branch and PR. Leave merge for manual approval when requested. Report exact commits, checks, failures and remaining decisions. Publishing a release, changing another Wiki's pin or deploying requires its own authority.
12. Keep a rollback plan with the prior consumer commit, prior release tag and full SHA, frozen locks and commands to reconstruct its derived output. Use a reviewed revert if a shared change must be reversed. Preserve intervening subject work and the audit trail. Deployment rollback follows the selected adapter and its separate authority.

## Bounded rc.14 to rc.15 example

The recipe `migrations/rc14-to-rc15.json` classifies the exact release delta. The read-only `wiki:update:review` helper checks exact-file mappings and explicitly reviewed adaptation hashes. It has no writer and does not verify remote release evidence or target conformance. Other release pairs need their own reviewed component inventory.

For this pair, qualify the guarded Graphify adapter before removing the obsolete Zensical patcher and its test. Carry Zensical's native checksum checker, build command, search/navigation adapters and browser checks together. Preserve the consumer's own identity, configuration and evidence. Read the Documentation guide for the test boundary and command examples.
