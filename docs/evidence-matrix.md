# Evidence matrix

| Claim | Support | State | Limitation |
|---|---|---|---|
| Persistent synthesis should compound rather than be rediscovered for every query. | SRC-001 | Supported | Requires lint and evidence safeguards against propagated errors. |
| OKF v0.2 is the portable knowledge foundation. | SRC-002 | Implemented candidate | Public schema endpoints are published through the documentation Pages site; validation still uses the pinned local schema copy. Hard validation, strict guidance, and unknown-field round-trip fixtures pass locally. |
| Human and LLM products should share canonical knowledge. | SRC-001, SRC-002, SRC-011 | Implemented candidate | More cross-renderer and independently maintained consumer fixtures are still needed. |
| A displayed governing question should be semantically distinct and use the active accent for both its rail and text. | SRC-009, SRC-012 | Implemented candidate (`DKBWS-HUMAN-002`) | The reference Zensical implementation has desktop/mobile browser evidence; broader cross-renderer evidence remains to be gathered. |
| Draft pages displayed in primary navigation should use a dedicated edit marker with readable status text, share the trailing control column with navigation chevrons, remain row-centred, and avoid page overflow. | SRC-005, SRC-009, SRC-017, SRC-018, SRC-020 | Implemented candidate (`DKBWS-HUMAN-003`) | The exact Pen Circle asset and geometry are reference-adapter decisions; other renderers still need equivalent built-output evidence. |
| Ordinary entry and architecture Mermaid diagrams should begin with renderer-default node treatment and reserve semantic styling for a recorded material distinction. | SRC-005, SRC-009, SRC-019 | Implemented candidate (`DKBWS-DESIGN-001`) | The pinned Zensical/Mermaid adapter has source, desktop, tablet, and mobile evidence; complex diagrams may still need a bounded, accessible, separately verified exception. |
| Zensical plus the DenchCo style should lead the reference distribution. | SRC-005, SRC-011, SRC-012 | Candidate preferred | Cross-renderer accessibility evidence remains incomplete. |
| Graphify adds useful explicit relationships but not evidence authority; a selected Graph profile must fail closed if either real 2D/3D route is absent. | SRC-006, SRC-009, SRC-011, SRC-012, SRC-020 | Implemented candidate (`DKBWS-GRAPH-001`) | Semantic extraction coverage varies by corpus; selective route runs remain diagnostic only. |
| A dedicated MCP is useful later but should not be required to read the standard. | SRC-002, SRC-007, SRC-008 | Adopted | MCP tool surface is not yet implemented. |
| Jujutsu should be included in DenchCo Standard Production maintenance workspaces, VCS root discovery must preserve filesystem-significant path bytes, and every file-changing development turn should end with a disclosed JJ commit rather than a subjective significance decision. | SRC-011, SRC-012, SRC-013, SRC-020 | Executable candidate (`DKBWS-PROV-001`) | Static and helper fixtures prove the mechanism, while historical adherence still requires reviewable turn-commit history. Portable Core and explicit distribution/CI checkouts remain Git-only compatible; Jujutsu 0.42.0 is available upstream but not yet reference-qualified beyond the locally tested 0.39.0 boundary. |
| One MIT License is the minimal clear permission for friends to reuse the repository's original work. | SRC-014 | Adopted | Third-party material and registered sources retain their own terms; the licence does not transfer ownership of the DenchCo name. |
| Shared Codex/Claude instructions should finish requested scope before offering at most three goal-linked recommendations and should park trigger-blocked work rather than repeat it. | SRC-011, SRC-012, SRC-015, SRC-016 | Implemented candidate (`DKBWS-PROMPT-001`) | Static checks prove instruction presence, import, and skill parity; model adherence remains behavioural and must be observed in consumer use. |
| Lifecycle comparison must use canonical source plus immutable commit and expose requirement changes even when descriptive version labels are equal. | SRC-020 | Implemented candidate (`DKBWS-UPDATE-001`) | Comparison requires the pinned commit and profile history to be present locally; unresolved or shallow-history cases block for manual review. |
| Reserved verification paths must contain schema-valid receipt/report artifacts, and ordinary consumers must not inherit Standard-maintainer synchronization commands. | SRC-020 | Implemented candidate (`DKBWS-VERIFY-001`, `DKBWS-VERIFY-002`) | The starter provides the governed boundary and a negative ad hoc-summary fixture; each consumer still maps its own gates and evidence. |
| A consumer starter needs complete security/source/licensing and proposal-handoff safeguards without inheriting the Standard's licence or remote-write authority. | SRC-014, SRC-020 | Implemented candidate (`DKBWS-SEC-001`, `DKBWS-PROMPT-001`) | The owner must still select the consumer licence and reporting channel; the Standard does not make those decisions. |
