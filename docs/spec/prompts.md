# Prompt and question contract

The canonical instantiation prompt is `prompts/instantiate-wiki.md`. It MUST be self-contained through repository-relative references and MUST NOT depend on machine-specific absolute paths after public release. The normative repository URL alone is a complete bootstrap invocation: the user MUST NOT be required to discover a prompt file, fill a field template, or supply a version, profile, Wiki URL, or deployment choice. Human guidance MAY route to <https://denchco.github.io/knowledge-base-wiki-documentation/>, but an implementation MUST resolve the current default-branch HEAD of <https://github.com/denchco/knowledge-base-wiki-standard> to an exact commit SHA before acting and MUST use that immutable commit as normative input for the complete run.

When the repository URL is the only bootstrap context, the implementation's first response MUST ask whether the wiki starts from a research topic seed—accepted as text, a file, folder, URL, or repository—or as a subject-empty local wiki. If the user already supplied either answer, the agent MUST use it without repeating the question. Where uncertainty remains material, agents ask one question at a time using `Question 1 of N`. Each answer informs the next question and `N` is revised as uncertainty changes. The agent MUST inspect a supplied seed and any existing target before asking follow-up questions, and MUST NOT ask the user to repeat discoverable title, topic, audience, governing-question, outcome, source, target-path, or design information.

For a research seed, the agent asks about expansion beyond the supplied source set only when the seed does not resolve that scope. For a subject-empty initialization, it asks for a project title but MUST NOT invent research claims, evidence, concepts, or a governing question. Privacy, licensing, retention, source authority, and target-boundary questions are conditional on unresolved material risk.

When target evidence activates `DKBWS-LINK-002`, the implementation agent adds stable anchors to the mapped source-register rows and makes each displayed source identity an individual relative link to its exact row. It checks direct links to named official authorities or publications against registered source URLs and preserves the target's declared identity grammar. A subject-empty or citation-free target remains not applicable and MUST NOT receive invented source identities or citations.

The agent MUST state the exact proposed accent colour and ask whether to use or replace it. It derives a candidate from evidenced branding or the existing target; otherwise it proposes the DenchCo default `#0b7285`. The rest of the accessible accent family and contrast token are derived automatically, recorded in `DESIGN.md`, and verified at a minimum 4.5:1 contrast ratio for normal accent-coloured text and 3:1 for non-text interactive boundaries against their rendered backgrounds. Standard Production, the immutable standard revision, an independent local target path, a conflict-free loopback Wiki URL, the platform-appropriate local service adapter, and deployment `none` are defaults rather than routine questions. Publication, remote repository creation, credentials, and external deployment remain separately authorised actions.

When Standard Production selects a persistent managed preview, the implementation MUST derive a project-unique stable service ID, serialize the shared-register load, conflict checks, live-listener probe, and atomic reservation publication under an exclusive user-local lock, publish the versioned static identity marker, and require exact registry, installation, load, and marker agreement for status. It MUST NOT stop, overwrite, or silently reassign an existing listener to resolve a collision. A requested preview is handed to the selected browser at the registered canonical URL only after identity-aware status passes; a temporary alternate-port browser server is build evidence, not managed-service evidence.

The prompt MUST include URL-only invocation, adaptive discovery, read order, authority, new-versus-existing migration policy, profile selection, dependency installation, Graphify, the `DKBWS-PROV-001` Git/Jujutsu boundary, identity-aware managed service reservation and exact browser handoff, verification, conformance, and a completion-first handoff. It MUST require every file-changing Standard Production development turn to finish with its persistent changes in a JJ commit after verification and state inspection, without a subjective substantive-work threshold and without empty commits for no-change turns. It MUST distinguish a Standard Production maintainer workspace from an explicit Git-only distribution/CI checkout. It MUST also distinguish the Standard repository from the independent target, automatically resolve and record an immutable revision, use `starter/starter.yaml` as the copy boundary, create subject content fresh, and record the target's automatically resolved local Wiki URL and no-deployment default unless the user explicitly authorises another deployment. Standard-maintainer documentation-sync commands remain outside the consumer dependency closure unless independently declared, and reserved verification paths contain only schema-valid receipt/report artifacts.

Next Steps are recommendations, not continuation authority. An agent includes them only when the user requests them, required work remains incomplete or blocked, or a named workflow requires a handoff. The list MUST contain no more than three items. Each item MUST map to an unfinished requested deliverable, a failed or unrun required check, or a decision requiring user authority; it MUST identify a target artifact or outcome, fit one follow-up pass, and state a completion condition.

The agent MUST apply a cycle guard before selecting an item. Bounded, parked, or evidence-blocked work is ineligible until new evidence appears, a scheduled recheck becomes due, or the user explicitly reopens it. Parked work records `blocked_by`, `reopen_when`, and `last_checked`. Optional adjacent research, generic improvements, passive waiting, invitations to continue, and filler are not Next Steps. If no candidate passes these gates, the handoff omits the section. A project MAY keep zero to three current priorities in its status record, but they are surfaced for status or roadmap work rather than appended automatically to unrelated responses.

An initialization planner MUST cite the canonical prompt, selected profile, and starter contract by content hash. All three, plus the Standard manifest and requirement catalogue, MUST be loaded from the same resolved commit; an explicit tag or abbreviated reference is resolved to an immutable commit rather than attached to current working-tree inputs. Planning does not authorize scaffolding: it MUST report existing-path collisions as preserve-and-review, MUST NOT create files, and MUST carry unresolved material inputs into the same sequential question protocol. Its layout MUST classify allowlisted subject-empty templates, target-authored subject content, and release-adapted implementation files; recursive root copying and reuse of the Standard corpus are forbidden.

Migration impact: bootstrap callers replace the entire field-based prompt with the normative repository URL. Implementation agents begin with seed-versus-subject-empty discovery, infer routine local defaults, ask for the accent choice, resolve the repository's current default-branch HEAD once, and record its exact commit SHA in the target manifest. Existing pinned consumers retain their content but must reconcile a missing or stale immutable revision before lifecycle planning can call them current. Subject-empty home pages replace the governing-question placeholder with an awaiting-seed notice and record `DKBWS-HUMAN-002` as not applicable until such a callout exists. Agent-profile consumers upgrading from `v0.1.0-rc.1` also add the completion/cycle policy to `AGENTS.md`, provide a root `CLAUDE.md` that imports `AGENTS.md` when Claude Code is supported, and separate active priorities from parked validation work. Standard Production maintainers additionally replace phase-by-significance wording with the prospective end-of-turn commit rule and its helper; existing JJ history is not rewritten. Consumers upgrading to `DKBWS-RUNTIME-002` inventory their register and live endpoint first, move only their own service on collision, add the static marker and fail-closed status fixture, then hand the exact registered URL to the selected browser. No OKF content migration is required.
