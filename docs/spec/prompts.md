# Prompt and question contract

The canonical instantiation prompt is `prompts/instantiate-wiki.md`. It MUST be self-contained through repository-relative references and MUST NOT depend on machine-specific absolute paths after public release. The normative repository URL alone is a complete bootstrap invocation: the user MUST NOT be required to discover a prompt file, fill a field template, or supply a version, profile, Wiki URL, or deployment choice. Human guidance MAY route to <https://denchco.github.io/knowledge-base-wiki-documentation/>, but an implementation MUST resolve the current default-branch HEAD of <https://github.com/denchco/knowledge-base-wiki-standard> to an exact commit SHA before acting and MUST use that immutable commit as normative input for the complete run.

When the repository URL is the only bootstrap context, the implementation's first response MUST ask whether the wiki starts from a research topic seed—accepted as text, a file, folder, URL, or repository—or as a subject-empty local wiki. If the user already supplied either answer, the agent MUST use it without repeating the question. Where uncertainty remains material, agents ask one question at a time using `Question 1 of N`. Each answer informs the next question and `N` is revised as uncertainty changes. The agent MUST inspect a supplied seed and any existing target before asking follow-up questions, and MUST NOT ask the user to repeat discoverable title, topic, audience, governing-question, outcome, source, target-path, or design information.

For a research seed, the agent asks about expansion beyond the supplied source set only when the seed does not resolve that scope. For a subject-empty initialization, it asks for a project title but MUST NOT invent research claims, evidence, concepts, or a governing question. Privacy, licensing, retention, source authority, and target-boundary questions are conditional on unresolved material risk.

When the seed supports a canonical governing question, the implementation maps its authoritative source and a bounded set of reader sources. Every exact repetition in that set is the same governed callout required by `DKBWS-HUMAN-002`; paraphrases, unrelated quotations, and historical/source records outside the bounded set remain neutral. The implementation proves exact-text consistency and visits every repetition route at desktop and mobile widths. Subject-empty and question-free targets record `DKBWS-HUMAN-004` as not applicable.

When target evidence activates `DKBWS-LINK-002`, the implementation agent adds stable anchors to the mapped source-register rows and makes each displayed source identity an individual relative link to its exact row. It checks direct links to named official authorities or publications against registered source URLs and preserves the target's declared identity grammar. A subject-empty or citation-free target remains not applicable and MUST NOT receive invented source identities or citations.

Standard Production initialization includes the tracked proposal-record directory and release-adapted proposal tooling required by `DKBWS-UPDATE-002`. A reusable consumer improvement is implemented, verified, and committed locally before one versioned proposal record is created. Preparation renders a deterministic sanitized payload with a stable marker, and user approval binds the exact repository, title, labels, body, and governed issue-form digest. Directly loaded records MUST satisfy the same state metadata, prerequisites, ordering, and terminal transitions as command-produced records. The agent MAY open the governed form after approval, but MUST NOT submit it, infer acceptance from issue closure, publish a release, or change the consumer's Standard pin. Decision, immutable-release inclusion, and later adoption remain separately authorised and recorded. Release observation requires exact registry bytes at the full recorded revision, strict release-to-registry ancestry, a matching public `draft: false`/`immutable: true` release, and exact tag resolution; the sole historical bridge is not a reusable intake mode.

The agent MUST state the exact proposed accent colour and ask whether to use or replace it. It derives a candidate from evidenced branding or the existing target; otherwise it proposes the DenchCo default `#0b7285`. The rest of the accessible accent family and contrast token are derived automatically, recorded in `DESIGN.md`, and verified at a minimum 4.5:1 contrast ratio for normal accent-coloured text and 3:1 for non-text interactive boundaries against their rendered backgrounds. Standard Production, the immutable standard revision, an independent local target path, a conflict-free loopback Wiki URL, the platform-appropriate local service adapter, and deployment `none` are defaults rather than routine questions. Publication, remote repository creation, credentials, and external deployment remain separately authorised actions.

When Standard Production selects a persistent managed preview, the implementation MUST derive a project-unique stable service ID, serialize the shared-register load, conflict checks, live-listener probe, and atomic reservation publication under an exclusive user-local lock, and publish the versioned static identity marker. Status MUST exact-match all twelve governed registration fields, the generated installed user-service definition, the loaded job, the canonical URL, and marker HTTP identity. It MUST NOT stop, overwrite, or silently reassign an existing listener to resolve a collision. A requested preview uses the fail-closed `service:preview` handoff and opens only the exact registered canonical URL after status passes; a temporary alternate-port browser server is build evidence, not managed-service evidence. Live status is maintainer-only evidence and remains `not-checked` in distribution/CI.

Under `DKBWS-PROMPT-002`, every user-facing Human or LLM Wiki destination in a development response MUST use a live absolute HTTP(S) URL rooted at the configured `human_wiki_url`. The captured-draft check covers Markdown destinations, entity-decoded HTML `a`/`area` links, and plain GFM-autolinked HTTP(S) text while masking code/comments and excluding image destinations. For a managed local origin, the agent runs the checker with `--managed-live` so exact service identity, canonical-origin equality, and HTTP 200 from every displayed route are proved during the turn. It MUST NOT substitute a repository-relative Markdown link, local absolute path, `file:` URL, or editor URL. A plain repository path MAY identify an implementation artifact with no rendered route, but it is not Wiki navigation. If a rendered route is unavailable, the response states that limitation rather than linking the source file. A host without a pre-send hook remains subject to the requirement but cannot be physically intercepted by repository code (`STD-VAL-007`).

The prompt MUST include URL-only invocation, adaptive discovery, read order, authority, new-versus-existing migration policy, profile selection, dependency installation, Graphify, the `DKBWS-PROV-001` Git/Jujutsu boundary, identity-aware managed service reservation and exact browser handoff, verified live-URL development responses, verification, conformance, and a completion-first handoff. It MUST require every file-changing Standard Production development turn to finish with its persistent changes in a JJ commit after verification and state inspection, without a subjective substantive-work threshold and without empty commits for no-change turns. It MUST distinguish a Standard Production maintainer workspace from an explicit Git-only distribution/CI checkout. It MUST also distinguish the Standard repository from the independent target, automatically resolve and record an immutable revision, use `starter/starter.yaml` as the copy boundary, create subject content fresh, and record the target's automatically resolved local Wiki URL and no-deployment default unless the user explicitly authorises another deployment. Standard-maintainer documentation-sync commands remain outside the consumer dependency closure unless independently declared, and reserved verification paths contain only schema-valid receipt/report artifacts.

Next Steps are recommendations, not continuation authority. An agent includes them only when the user requests them, required work remains incomplete or blocked, or a named workflow requires a handoff. The list MUST contain no more than three items. Each item MUST map to an unfinished requested deliverable, a failed or unrun required check, or a decision requiring user authority; it MUST identify a target artifact or outcome, fit one follow-up pass, and state a completion condition.

The agent MUST apply a cycle guard before selecting an item. Bounded, parked, or evidence-blocked work is ineligible until new evidence appears, a scheduled recheck becomes due, or the user explicitly reopens it. Parked work records `blocked_by`, `reopen_when`, and `last_checked`. Optional adjacent research, generic improvements, passive waiting, invitations to continue, and filler are not Next Steps. If no candidate passes these gates, the handoff omits the section. A project MAY keep zero to three current priorities in its status record, but they are surfaced for status or roadmap work rather than appended automatically to unrelated responses.

An initialization planner MUST cite the canonical prompt, selected profile, and starter contract by content hash. All three, plus the Standard manifest and requirement catalogue, MUST be loaded from the same resolved commit; an explicit tag or abbreviated reference is resolved to an immutable commit rather than attached to current working-tree inputs. Planning does not authorize scaffolding: it MUST report existing-path collisions as preserve-and-review, MUST NOT create files, and MUST carry unresolved material inputs into the same sequential question protocol. Its layout MUST classify allowlisted subject-empty templates, target-authored subject content, and release-adapted implementation files; recursive root copying and reuse of the Standard corpus are forbidden.

Migration impact: bootstrap callers replace the entire field-based prompt with the normative repository URL. Implementation agents begin with seed-versus-subject-empty discovery, infer routine local defaults, ask for the accent choice, resolve the repository's current default-branch HEAD once, and record its exact commit SHA in the target manifest. Existing pinned consumers retain their content but must reconcile a missing or stale immutable revision before lifecycle planning can call them current. Subject-empty home pages replace the governing-question placeholder with an awaiting-seed notice and record `DKBWS-HUMAN-002` and `DKBWS-HUMAN-004` as not applicable until a canonical question is declared; seeded consumers map its authoritative source and bounded reader set, then govern every exact repetition. Agent-profile consumers upgrading from `v0.1.0-rc.1` also add the completion/cycle policy to `AGENTS.md`, provide a root `CLAUDE.md` that imports `AGENTS.md` when Claude Code is supported, separate active priorities from parked validation work, declare `development_response_links: live-wiki` plus an absolute `human_wiki_url`, install the response-link checker, and replace Wiki file links in development responses with verified live routes. They upgrade the checker to cover HTML and plain GFM destinations and use `--managed-live` for local managed responses; the pre-send host limitation remains explicit. Standard Production maintainers additionally replace phase-by-significance wording with the prospective end-of-turn commit rule and its helper; existing JJ history is not rewritten. Consumers upgrading to `DKBWS-RUNTIME-002` inventory and exact-match all twelve governed registration fields, reinstall the exact current job definition, prove it loaded, add the marker, and use the fail-closed canonical preview handoff; distribution/CI does not claim live evidence. Standard Production proposal-intake consumers validate direct states, freeze terminal transitions, migrate each ignored draft to one governed tracked record, and require exact registry-revision/ancestry/public-release evidence before recording release inclusion. They MUST NOT use the one historical bridge for new work. No OKF content migration is required.
