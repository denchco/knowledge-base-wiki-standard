## Governing-question rendering

`DKBWS-HUMAN-002` is conditional on presenting a governing-question callout; it does not require every Human Wiki to invent one. A conforming renderer MAY choose its native semantic element, but the built output MUST expose a stable `governing-question` marker so agents and verification tools can distinguish the callout from quoted evidence.

The Zensical reference adapter uses `<blockquote class="governing-question">`. Its rail and question text resolve from the same active accent token at every supported viewport, while unmarked blockquotes retain the renderer's neutral quotation treatment. Source markup or CSS inspection alone cannot prove this rendered requirement.

Migration from a release without this rule requires three reviewable changes where a governing-question callout already exists: add the semantic marker, bind both rendered colours to the active accent family, and add browser evidence that compares computed colours with the resolved token. A project with no governing-question callout records the requirement as not applicable rather than creating decorative content.

## Canonical governing-question consistency

`DKBWS-HUMAN-004` closes the inverse gap left by styling only already-designated callouts. An implementation that declares one canonical governing question maps its authoritative source and a finite reader-source set. Within that set, an exact repetition cannot appear as an ordinary paragraph or unmarked quotation: it uses the same governed callout marker and presentation on every route. The source gate compares the exact canonical string rather than guessing at semantic similarity, and the browser gate visits every discovered repetition route at desktop and mobile widths.

The `governing_question` role identifies semantic authority, not a required separate document. It MAY map the same file as `human_wiki` when the authoritative wording lives on the Human Wiki entry page; other unrelated role collisions retain the manifest diagnostic.

The rule is deliberately exact and bounded. A paraphrase, an unrelated quotation, a historical amendment, or a source record outside the declared reader set is not silently restyled. A project that cannot map an authoritative canonical source MAY instead declare an explicit route allowlist, but it MUST still prove that each listed route contains exactly one matching governed callout and MUST NOT claim repository-wide equality coverage. A subject-empty Wiki or a Wiki with no declared canonical question records the requirement as not applicable and invents nothing.

Migration identifies the authoritative question source, declares the bounded reader sources, wraps every existing verbatim reader-facing repetition in the governed component, and records all resulting routes in the built-output browser proof. Question wording and evidence do not change. Upgrade tooling reports unmatched repetitions and preserves local deviations; it does not rewrite prose automatically.

## Draft navigation rendering

`DKBWS-HUMAN-003` is conditional on rendering draft state inside primary navigation; it does not require lifecycle markers in a Wiki that omits them. The visible marker supplements, rather than replaces, readable status text exposed through a tooltip or equivalent accessible description. Other lifecycle states must not inherit draft artwork.

The Zensical reference adapter maps `.md-status--draft` to the registered CC0 Pen Circle asset, exposes “Draft — research in progress”, and sizes the marker so its trailing centre matches the stock nested-navigation chevron. Its browser evidence also compares each control's vertical centre with its own navigation row and rejects page overflow. Another renderer MAY use an equivalent open-licensed draft-edit glyph and native status affordance when its own built-output check proves the same semantic distinction and alignment outcome.

Migration from a generic information marker requires the dedicated draft asset, readable status mapping, renderer-local alignment rule, third-party licence record, and positive browser evidence. A simpler renderer without navigation status markers records the conditional requirement as not applicable; it need not add decoration solely for conformance.

## Reader evidence navigation

`DKBWS-LINK-002` closes the route between a rendered claim and its governed evidence record. For the Standard `SRC-NNN` grammar, `[SRC-001](sources.md#src-001)` renders as the visibly bracketed citation `[SRC-001]`, remains one keyboard-focusable link with an intelligible source-ID name, and reaches the row carrying the stable `src-001` anchor. A list retains one link per identity. A compact range links only its two displayed endpoints; it does not imply that hidden intermediate records were inspected.

The requirement is conditional. A subject-empty Wiki, an agent-only bundle, or a Human Wiki that displays no source identities does not invent citations to satisfy it. Equivalent mapped source-register paths, identity grammars, anchors, and renderers remain valid when their lint and built-output evidence prove the same reader route. Automatic rewriting is optional; a lint-only checker plus manually authored links is a conforming fallback.

Migration first adds stable row anchors to the mapped source register, then converts visible identities to individual exact-row links, checks named authority URLs against registered source URLs, preserves declared local citation grammar and deviations, and records a browser journey to a representative destination row. Upgrade planning reports these changes for review and MUST NOT rewrite canonical content automatically.

## Managed local preview identity

`DKBWS-RUNTIME-001` remains the baseline HTTP check for any runtime. `DKBWS-RUNTIME-002` applies only when a project claims a restart-resilient or otherwise persistent managed preview. Foreground and ephemeral verification servers do not acquire a service-management obligation, but neither can they prove the managed-preview requirement.

The shared register is a user-scoped, adapter-documented inventory with a versioned root and entries keyed by stable service ID. The Standard's macOS reference entry exact-matches twelve governed fields: `serviceId`, `projectRoot`, `host`, `port`, `healthPath`, `packagePath`, `url`, `command`, `label`, `plistPath`, `stdoutLog`, and `stderrLog`. Its installed LaunchAgent plist must be byte-identical to the job generated from the current project, runtime, endpoint, label, environment, and log contract; the expected launchd job must also be loaded. A stale command, path, log, plist, URL, or adapter label therefore fails status even when the endpoint returns HTTP 200. Another operating-system adapter MAY choose its native user-service mechanism and register location while preserving the same exact declared registration and installed/loaded job semantics.

Reservation follows one fail-closed sequence:

1. Derive a project-unique stable service ID, candidate loopback endpoint, and `/assets/service-identity.json` health path.
2. Acquire the adapter's exclusive user-local registry lock with a bounded wait. Recover a stale lock only after its age exceeds the documented threshold and its recorded owner process is no longer live.
3. While holding that lock, reload the register, reject the same service ID owned by another project or any overlapping host/port assignment, and probe an exclusive bind to detect an unregistered live listener. Do not kill, overwrite, or silently reassign another service.
4. Publish a static marker conforming to `service-identity-v1` with `schemaVersion: 1` and the exact service ID, then atomically replace the complete register from a same-directory temporary file before releasing the lock.
5. Install and load the selected user-service adapter. Status passes only when all twelve governed registration fields, the exact installed service definition, the loaded job, the registered canonical URL, and the identity marker response agree.
6. When the user asks for a preview, use the status-gated preview command. It refuses to invoke the browser on any failed component or URL mismatch, opens only the exact registered canonical URL, and reports an opener failure instead of claiming success. An available port chosen only for a test process is separate evidence for `DKBWS-RUNTIME-001`.

The reference command is `npm run service:preview`. Complete verification runs live `service:status` only in a Standard Production maintainer workspace, where the registered service is expected to exist. An explicit distribution/CI checkout has neither authority nor stable user-service state to supply that evidence, so `DKBWS-RUNTIME-002` and `local_service` remain `not-checked` there rather than being inferred from fixtures or an ephemeral browser server.

Migration from an HTTP-only managed preview first inventories its current service ID, endpoint, register entry, adapter state, and live listener. If the endpoint is already owned or occupied, select an actually free loopback port and update the package service configuration, manifest URL, renderer URL, documentation, and register as one reviewable change. Then add the versioned marker, identity-aware status fixtures, install/start the adapter, and prove the exact canonical browser handoff. Existing foreground-only consumers record `DKBWS-RUNTIME-002` as not applicable unless they choose a persistent adapter.

## Development response navigation

`DKBWS-PROMPT-002` governs the links an agent displays to the user after development work. Human- or LLM-Wiki navigation uses the configured `human_wiki_url` origin and a rendered route, not the canonical Markdown file that generated it. The configured origin is an absolute HTTP(S) URL. For a persistent local preview, the exact registered service identity and route must be healthy during the turn before the response calls the URL live; an ephemeral verification origin cannot silently replace it.

The response-link linter checks the navigation forms a rendered development response can expose: inline and reference Markdown destinations, Markdown autolinks, entity-decoded HTML `a` and `area` `href` attributes, and plain HTTP(S) text that GFM turns into an autolink. It masks fenced/inline code and HTML comments and does not treat image destinations as user-facing navigation. It rejects repository-relative or absolute clickable file paths, `file:` and editor schemes, and Wiki URLs on another local origin or outside the configured base path. Plain repository paths remain available as non-navigation text for scripts, schemas, or other implementation artifacts with no rendered route.

For a managed local Wiki, `npm run response:links:check -- --base-url <canonical-url> --managed-live` additionally requires exact registration, installed service definition, loaded job, static-marker identity, equality between configured and registered canonical URLs, and HTTP 200 from every displayed Wiki route. `DKBWS-RESPONSE-LINK-LIVE-IDENTITY-001`, `DKBWS-RESPONSE-LINK-LIVE-BASE-001`, and `DKBWS-RESPONSE-LINK-LIVE-ROUTE-001` distinguish those failures. If the host does not expose a pre-send response hook, instruction parity and fixtures make a violation detectable and nonconforming but cannot physically intercept an uncaptured model response; `STD-VAL-007` remains the explicit host boundary.

Migration adds `development_response_links: live-wiki` and an absolute `human_wiki_url` to the manifest, installs the managed instruction block and response-link checker, replaces response file links with rendered routes, and verifies every displayed managed-local route before handoff. An unavailable route is reported as unavailable; it is not replaced with a clickable source file.

## Lifecycle identity and migration

`DKBWS-UPDATE-001` treats a version label as descriptive metadata, not an immutable identity. A lifecycle comparison first requires the same Standard name and canonical source, resolves both revisions to commits, compares ancestry, loads the manifest, selected profile, and requirement catalogue from those exact commits, and reports introduced or removed inherited requirement IDs. A missing, unresolved, newer, or diverged consumer revision is a manual blocking action. Candidate hashes must describe the same immutable revision named in the report; a dirty working-tree file must never be labelled as `HEAD` evidence.

Migration from a manifest without `standard.revision` first records a resolvable immutable commit and reconciles its version label with the Standard manifest at that commit. A same-version older revision still requires review and repinning when the candidate adds requirements. Source changes are identity changes, not automatic version upgrades.

## Consumer-to-Standard proposal lifecycle

`DKBWS-UPDATE-002` makes the tracked proposal record authoritative; an ignored Markdown draft or generated GitHub payload is disposable output. The versioned record preserves one stable proposal identifier, originating project and optional public URL, full Git-compatible implementation commit, optional Jujutsu change ID, pinned Standard revision, proposed reuse classification, affected contract, implementation and verification evidence, dependencies, limitations and fallback, licensing and disclosure state, applicable accessibility/browser evidence, and the complete upstream and downstream lifecycle.

The lifecycle records local observation, implementation and verification; payload preparation and approval; issue submission or linkage; upstream classification and explicit decision; acceptance, rejection, or withdrawal; immutable-release inclusion; and later consumer adoption as distinct transitions. Validation checks direct state as well as command transitions: unprepared/pending/not-submitted/not-considered states retain no outcome metadata; preparation requires complete implementation and passing verification; submission or linkage requires a prepared payload and current approval; exact issue identity, number, observed state, digest, and transition timestamps agree; a decision requires linked governed intake; accepted requirement IDs are codepoint-sorted; release inclusion requires acceptance; and adoption targets the exact included revision with matching authority/transition time. Submission observation, issue linkage, decision, release inclusion, and adoption are one-way or terminal in workflow v1. Loading hand-edited JSON therefore cannot bypass a command precondition.

A GitHub issue URL or open/closed state is linkage evidence only. Acceptance requires an explicit Standard decision. Release inclusion is recorded only after read-only checks resolve the full `registryRevision` exactly, load and validate the registry bytes from that revision, prove the registry revision is strictly descended from the release revision, verify a public GitHub release whose exact tag has `draft: false` and `immutable: true`, and prove that tag resolves to the recorded release revision. `DKBWS-PROP-STATE-TRANSITION-001`, `DKBWS-PROP-REGISTRY-REVISION-001`, `DKBWS-PROP-REGISTRY-ANCESTRY-001`, and `DKBWS-PROP-RELEASE-IMMUTABLE-001` distinguish these state and release failures. Consumer adoption is a later, separately authorised pin and migration decision.

Payload preparation deterministically renders the exact repository, title, labels, and body, includes a stable hidden proposal marker, and binds approval to those bytes plus the governed issue-form SHA-256. Any edit or form change clears the approval. Duplicate proposal identifiers and markers fail validation; after an ambiguous network outcome, read-only reconciliation searches by marker instead of preparing another submission. Validation, verification, payload preparation, display, and synchronization checks never write remotely. Opening the governed public form may navigate a local browser and present the approved payload, but the user performs the final submission; if the form is absent or its digest differs, the workflow fails closed.

The `pre-registry-local-history` intake mode is not a general migration escape hatch. Workflow v1 accepts only registry entry `DKBWS-PROP-uk-digital-health-reader-source-navigation-38f4b5cbcddce10fbcde32f70862143b`: project `UK Digital Health compliance`, no public URL or issue, implementation commit `3a085ebbfa66dea87d96700c7a735cf65def5ef6`, verification commit `3d9e1379ec67fd378b16c4b50c77f57c0db3c871`, pinned Standard revision `46183bc02c3d818f5aac962a4fbebc49b6ac9659`, reusable/accepted decision revision `6b9c686c66d2ef0e17342d666140bf4117f33a87`, and accepted requirement `DKBWS-LINK-002`. Any other use fails `DKBWS-PROP-HISTORICAL-BRIDGE-001`; consumer proposal records still require governed issue linkage before a decision.

Migration converts each existing ignored proposal draft into one tracked schema-valid record without inventing approval, an issue URL, a maintainer decision, or a release. New and previously unregistered work uses governed issue intake; it cannot copy the historical bridge mode. A locally accepted but unreleased improvement remains pending immutable-release inclusion. Generated sanitized payloads stay under the declared ignored output path, and any later record, decision, release, or adoption change is committed through the repository's normal Jujutsu verification phase.

## Verification artifact names

For the reference verification adapter, `output/verification/receipt.json` is reserved for `schema/verification-receipt-v1.json` and `output/verification/conformance-report.json` is reserved for its paired `schema/conformance-report-v1.json` output. A consumer-specific build or browser summary uses a distinct filename. Migration renames an ad hoc summary, emits explicit gate IDs, exit codes, evidence and requirement results, then validates both reserved artifacts before claiming complete conformance.

## Consumer dependency boundary

Standard-maintainer documentation synchronization is not part of an ordinary consumer's `DKBWS-VERIFY-001` closure. An implementation agent must exclude `sync:documentation:*`, `verify:workspace`, and the sibling-documentation contract unless that consumer separately declares, implements, and verifies its own synchronization capability. Consumer licensing is likewise an explicit owner decision; the starter records the decision and third-party boundary without inheriting the Standard repository's MIT licence automatically.
