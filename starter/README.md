# Subject-empty starter

This directory is the reusable starting surface for an independent knowledge-base repository. It is not a copy of the DenchCo standard repository and it contains no example topic, standard help corpus, dogfood evidence, or deployment choice.

Use `starter.yaml` as the machine-readable boundary. A Codex instance should:

1. accept the standard repository URL as the complete bootstrap invocation;
2. ask first for a research topic seed or a subject-empty local initialization, then inspect before asking follow-ups;
3. resolve the latest published, non-draft, native-immutable release with `npm run standard:stack -- resolve --json`, verify its exact tag/SHA and trusted successful `Verify` push/main evidence, then inspect that released commit;
4. infer routine local defaults, state and confirm the accent hex, and render only the listed templates into a separate target repository;
5. render the target's `AUTHORING.md` policy and author its `docs/` and `knowledge/` content from its own topic and sources, or preserve an explicit awaiting-seed state without invented claims;
6. adapt only the explicitly classified implementation files needed by the selected profile; and
7. reserve the target's conflict-free loopback Wiki URL through a serialized, atomically published shared-register transaction with live-listener preflight, install its project-unique static service marker and platform user-service adapter, default deployment to none, and validate the completed target against the pinned standard revision.

The rendered starter installs one shared agent contract in `AGENTS.md`, a root `CLAUDE.md` import for Claude Code, security/source/licensing boundaries, exact reader-to-source-row navigation when citations exist, canonical governing-question consistency when a question is declared, correct 2D and 3D graph mount hooks, and a project-status record that keeps active priorities separate from parked work. Seeded targets map the authoritative question and bounded reader sources; subject-empty targets omit that mapping and record the conditional requirement as not applicable. Standard Production instructions close every file-changing development turn with a disclosed JJ commit after verification and state inspection; there is no subjective “substantive work” threshold and no empty commit for a no-change turn. After every development cycle, the agent assesses the continuing subject and reports up to three prioritised content-first updates using `Proposed update:`, `Why it matters:` and `Done when:`, or an explicit no-update outcome. Completion-first work, required verification, the cycle guard and separate execution authority remain in force.

The starter also declares `development_response_links: live-wiki`. Development responses navigate Human or LLM Wiki content only through verified absolute HTTP(S) routes at the target's configured canonical Human Wiki origin. File/editor URLs and clickable local or repository-relative paths do not substitute for Wiki navigation; a plain path may identify only a non-Wiki implementation artifact. Adapted Standard Production tooling checks Markdown, entity-decoded HTML links, and plain GFM-autolinked URLs with `npm run response:links:check -- --base-url <canonical-url>`; managed local handoffs add `--managed-live` for exact service identity, canonical URL equality, and HTTP 200 from every displayed route. An unavailable route is disclosed, and absolute interception of an uncaptured response remains dependent on a host-provided pre-send hook under `STD-VAL-007`.

The consumer agent contract also preserves reusable improvements as tracked `standard-proposals/` records. Local validation checks direct-state metadata, prerequisites, and terminal transitions; generated payloads under `output/standard-proposals/` are disposable. The thin proposal CLI checks the governed form, labels, immutable payload digest, and marker before it may open the user's browser, but it never submits an issue or uploads a file. Release observation requires exact registry-revision bytes, strict release-to-registry ancestry, the matching public non-draft immutable tag, and exact tag resolution. The Standard's sole historical bridge is never available to new consumer work. Intake, explicit Standard acceptance, immutable release inclusion, and optional consumer adoption remain separate authorised JJ phases; none silently changes the target's Standard pin or conformance claim.

Every new Wiki receives the standalone `AUTHORING.md` policy and a manifest `authoring_policy` mapping. The DenchCo ASD-STE100-inspired 80% house style applies to all new original English Wiki prose without another routine bootstrap question. 80% is a pragmatic aim, not a computed score or a claim of ASD-STE100 compliance. Apply the core habits and record material exceptions with their scope and reason. Preserve quotations, code, identifiers, official names, necessary technical terms, source claims, uncertainty, normative obligations, and exact governing-question wording. Follow explicit user instructions and stricter applicable local policy. Existing prose is not subject to a bulk rewrite, and the default does not change consumer pins.

The public human documentation is at <https://denchco.github.io/knowledge-base-wiki-documentation/>. The standard repository at <https://github.com/denchco/knowledge-base-wiki-standard> remains the sole normative authority.

Do not recursively copy the repository root. Do not publish the standard's reference pages as the target Wiki.

There is no apply command in this candidate. The templates define a deterministic content boundary, not a secretly incomplete runnable scaffold. Portable Core targets validate with the CLI and schemas from the pinned release. Standard Production additionally requires an implementation agent to supply and verify the complete consumer renderer, scripts, schemas, profiles, runtime assets, locks, CI, and provenance closure selected from that release. Standard-maintainer documentation-sync commands and `verify:workspace` stay out unless the consumer independently declares that capability. Reserved verification paths hold a verification-receipt-v1 artifact and the paired conformance report; project-only summaries use a different path.

## Frozen release stack

The release fixes the tool versions, dependency locks, configuration contracts and verification implementation used for the first build. Install its frozen locks, including `npm ci` and `uv sync --frozen`. Target-owned content, confirmed appearance and documented deviations remain independent. New improvements require a new verified immutable release.

Semantic version ordering includes prereleases such as `rc.8`. Selection fails when the newest eligible release lacks exact successful evidence; it does not substitute `main` or an older release. Explicit historical/development `--standard-revision` plans remain unverified release selections.

Carry `standard-stack.mjs`, `standard-stack-cli.mjs`, `standard-stack.test.mjs`, `standard-stack-report-v1.json` and the `standard:stack` package command together. Existing Wikis run `npm run standard:stack -- check <wiki>` to inspect release availability. This command never installs, changes pins or migrates files. An authorised migration checks compatibility and deviations, preserves unknown fields, and passes complete selected-profile verification. A dated release pass does not clear newly reported vulnerabilities or waive current audits.

## Appearance adapter candidate

The local candidate includes a versioned appearance input template and reusable generator. Render the confirmed accent into `config/wiki-appearance.json`; honour explicit reader-default instructions for `appearance` and `width`. New Wikis start with light appearance and Wide desktop width, including when the appearance configuration is absent. An explicit configured Standard default and valid saved reader choices take precedence. Missing, invalid or unavailable storage uses the configured width or Wide when no width is configured. Mobile keeps its contained layout and hidden width control without changing the saved desktop choice. Existing consumers adopt this default through a reviewed migration; their pins remain unchanged.

Carry `scripts/wiki-appearance.mjs`, `scripts/prepare-wiki-appearance.mjs`, the versioned schema, configured width fallback, graph integration and their tests together. Run `prepare:appearance` before Zensical, build from `zensical.appearance.toml`, and use that input in live-config preparation. Ignore `zensical.appearance.toml` and `docs/assets/appearance/`, and declare them as derived verification outputs. Run the appearance unit and real-renderer browser checks as part of complete verification. This adapter does not make the overall starter an apply command. Its release and later consumer adoption remain separate recorded events.
